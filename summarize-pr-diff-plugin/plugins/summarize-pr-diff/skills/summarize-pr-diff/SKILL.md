# PR diff 요약 (리뷰어용)

이 스킬의 목표는 **리뷰어가 diff를 직접 다 읽기 전에**, "무엇이 / 왜 바뀌었고 / 어디를
주의 깊게 봐야 하는지"를 30초 안에 파악하도록 돕는 것입니다. 변경을 평가(코드 리뷰)하는
게 아니라 **이해를 돕는 요약**이 목적입니다. 한국어로, 간결하게 씁니다.

## 1. diff와 맥락을 수집한다

요약은 diff만 봐서는 반쪽입니다. "왜"는 보통 PR 설명과 커밋 메시지에 있으니 함께 모으세요.

**GitHub PR이 지정된 경우** (PR 번호, URL, 또는 "PR #123" 언급):

- `gh pr view <번호> --json title,body,author,commits,additions,deletions,changedFiles` — 제목·본문·커밋·규모
- `gh pr diff <번호>` — 실제 diff

**로컬 변경인 경우** (PR 지정 없이 "이 브랜치", "내 변경사항" 등):

- base 브랜치를 먼저 확인합니다. 보통 `main`이지만, 확실치 않으면
  `git rev-parse --abbrev-ref origin/HEAD`로 기본 브랜치를 확인하세요.
- `git diff <base>...HEAD --stat` — 변경 규모/파일 목록 (점 3개 `...`로 분기점 기준 비교)
- `git log <base>..HEAD --oneline` — 커밋 메시지(= "왜"의 단서)
- `git diff <base>...HEAD` — 실제 diff

> diff가 큰 경우(수백 줄+): 먼저 `--stat`과 커밋 로그로 큰 그림을 잡고, 핵심 파일만
> 골라 실제 diff를 읽으세요. lock 파일·생성된 파일·대량 포맷팅 변경은 한 줄로 묶어
> 언급하고 본문을 다 읽지 않습니다. 토큰과 시간을 변경의 핵심에 쓰는 게 중요합니다.

이 환경은 Windows PowerShell입니다. `gh`/`git` 명령은 Bash 도구로 실행하면 됩니다.

## 2. 변경을 "기계적 나열"이 아니라 "의도 단위"로 묶는다

리뷰어에게 파일별 +/- 나열은 도움이 안 됩니다. 변경을 **무엇을 하려던 작업인지**로
묶으세요. 예: "결제 에러 처리 추가"라는 한 의도가 `route.ts`, `errors.ts`,
`logger.ts` 세 파일에 흩어져 있다면, 파일 3개가 아니라 의도 1개로 묶어 설명합니다.
diff에서 이 그룹핑을 읽어내는 것이 이 스킬의 핵심 가치입니다.

## 3. 리뷰어가 주의할 부분을 짚는다

요약의 가장 유용한 부분입니다. diff에서 아래 같은 신호가 보이면 명시적으로 언급하세요
(없으면 억지로 만들지 말 것):

- 공개 API/인터페이스 시그니처 변경, 호환성 깨짐
- 새 의존성 추가, 설정·환경변수·인프라/마이그레이션 변경
- 대량 삭제, 파일 이동/리네임(로직 변경과 섞여 있으면 특히)
- 에러 처리·인증·권한·보안에 닿는 변경
- TODO/FIXME, 임시 코드, 주석 처리된 코드, 디버그 로그 잔존
- 테스트가 함께 바뀌었는지 / 변경에 비해 테스트가 비어 있는지

평가가 아니라 **"여기를 눈여겨보라"는 안내**입니다. 단정적인 지적("이건 버그다")보다는
리뷰 포인트로 제시하세요.

## 4. 아래 구조로 출력한다

간결함이 핵심입니다. 각 항목은 불릿 1~2줄. 해당 없는 섹션은 통째로 생략합니다.

```markdown
## 📋 PR 요약: <제목 또는 한 줄 요약>

**한 줄**: <이 PR이 하는 일을 한 문장으로>
**규모**: 파일 N개 · +X / −Y (정보가 있을 때만)

### 무엇이 바뀌었나

- **<의도/영역 1>**: <무엇을 어떻게>
- **<의도/영역 2>**: ...

### 왜

- <PR 설명·커밋에서 읽어낸 배경/목적. 불명확하면 "PR 설명/커밋에 명시 없음"이라고 솔직히>

### 👀 리뷰 시 주의할 부분

- <위 3번의 신호들. 없으면 이 섹션 생략>
```

**규모 감각**: 전체 요약은 길어도 화면 한 눈에 들어오는 분량을 넘기지 마세요. 변경이
작으면 그만큼 더 짧게. 리뷰어의 시간을 아끼는 것이 이 스킬이 존재하는 이유입니다.

## 예시 (감 잡기용)

작은 버그픽스 PR이라면 이 정도로 충분합니다:

> ## 📋 PR 요약: 피드백 폼 제출 시 중복 호출 방지
>
> **한 줄**: 제출 버튼 연타로 API가 중복 호출되던 문제를 제출 중 비활성화로 막음.
> **규모**: 파일 2개 · +18 / −3
>
> ### 무엇이 바뀌었나
>
> - **중복 제출 방지**: `FeedbackForm.tsx`에 `isSubmitting` 상태 추가, 제출 중 버튼 disable.
> - **테스트**: 연타 시 핸들러가 1회만 불리는 케이스 추가.
>
> ### 왜
>
> - 사용자 제보로 중복 피드백이 쌓이던 이슈 대응 (커밋 메시지 기준).
>
> ### 👀 리뷰 시 주의할 부분
>
> - 제출 실패 시 `isSubmitting`이 다시 false로 풀리는지 확인 필요.
